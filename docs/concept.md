# Part 1. 프로젝트 정의

## 1. 프로젝트 개요

World Observatory는 시드 기반으로 생성된 세계가 시간이 흐르면서 스스로 변화하는 과정을 관찰하는 시뮬레이션이다.

사용자는 세계를 직접 세밀하게 조종하는 대신 다음 역할 중 하나를 선택한다.

### 1.1 관찰자

- 세계의 시간을 진행한다.
- 도시의 성장과 쇠퇴를 관찰한다.
- 자연재해와 사회적 사건을 확인한다.
- 사건이 발생한 이유와 결과를 추적한다.
- 인구, 식량, 기후, 이주 흐름을 시각화한다.

### 1.2 관리자

- 식량 원조를 제공한다.
- 재난 대응 수준을 정한다.
- 이민과 교역 정책을 조절한다.
- 도시 간 도로와 기반 시설을 확충한다.
- 제한된 자원으로 문제에 대응한다.

### 1.3 세계 편집자

- 가뭄, 홍수, 전염병 등의 사건을 직접 발생시킨다.
- 특정 지역의 기후나 자원을 변경한다.
- 새로운 도시나 정착지를 추가한다.
- 과거 시점으로 돌아가 다른 조건을 적용한다.
- 원래 역사와 대체 역사를 비교한다.

## 2. 핵심 가치

이 프로젝트의 핵심은 단순히 무작위 사건을 많이 보여주는 것이 아니다.

다음 세 가지 질문에 답할 수 있어야 한다.

### 2.1 왜 발생했는가?

예:

> 아렌 도시의 인구는 지난 5년 동안 18% 감소했다.  
> 주요 원인은 식량 부족 47%, 외부 이주 28%, 전염병 19%, 기타 6%다.

### 2.2 이후 무엇이 발생할 수 있는가?

예:

> 현재 식량 부족이 8개월 이상 지속되고 있다.  
> 현재 상태가 유지된다고 가정할 때 이번 달 식량 폭동 발생 확률은 32%, 대규모 이주 발생 확률은 58%다.

확률의 의미가 중요하다. 여기에 표시하는 모든 확률은 **현재 상태 기준 조건부 확률**이다. §13의 확률 엔진이 이번 틱에 계산하는 값을 그대로 보여주는 것이지, 미래의 상태 변화를 따라가는 예측이 아니다. 여러 미래 경로를 실제로 시뮬레이션하는 몬테카를로 예측은 장기 확장 범위(§5)로 미룬다. UI의 라벨도 "현재 상태 기준"이라고 명시해 사용자가 예측으로 오해하지 않게 한다.

### 2.3 다른 선택을 했다면 어떻게 되었을까?

예:

> 가뭄 발생 직후 식량을 지원한 대체 역사에서는 내전이 발생하지 않았고, 20년 후 인구가 원래 역사보다 27% 많았다.

# Part 3. 핵심 설계 원칙

## 6. 시뮬레이션 우선 원칙

세계 상태는 규칙 기반 시뮬레이션 엔진이 관리한다.

LLM은 다음 역할만 담당한다.

- 사건 후보 제안
- 사건 설명 작성
- 새로운 이벤트 템플릿 초안 생성
- 연쇄 사건 후보 제안
- 정책 선택지 제안
- 역사 기록 요약
- 현재 상태에 대한 자연어 설명

LLM은 다음 작업을 직접 수행하지 않는다.

- 인구 수치를 직접 변경
- 식량 재고를 직접 변경
- 실제 사건 발생 여부를 최종 결정
- 확률 난수를 직접 생성
- 검증되지 않은 속성을 세계에 추가
- 시뮬레이션 상태를 직접 저장
- 허용되지 않은 코드를 실행

핵심 원칙은 다음과 같다.

> LLM은 제안하고, 규칙 엔진은 검증하고, 결정론적 시뮬레이션이 실행한다.

## 7. 결정론 원칙

동일한 조건에서는 동일한 결과가 나와야 한다.

동일 결과를 만드는 입력은 다음과 같다.

- 세계 시드
- 생성기 버전
- 시뮬레이션 버전
- 세계 설정
- 이벤트 템플릿 버전
- 사용자 개입 기록
- 승인된 LLM 이벤트 정의

배속은 결과에 영향을 주지 않아야 한다.

다음 두 실행 결과는 같아야 한다.

- 1배속으로 세계 시간 100년 진행
- 100배속으로 세계 시간 100년 진행

시뮬레이션 내부에서 `Math.random()`을 사용하지 않는다.

각 난수는 다음과 같은 파생 시드를 사용한다.

```text
randomSeed = hash(
  worldSeed,
  simulationVersion,
  currentTick,
  systemName,
  entityId,
  randomPurpose
)
```

### 7.1 허용 수치 연산 (크로스 브라우저 결정론)

`Math.sin` 같은 초월함수는 브라우저 엔진마다 결과가 다를 수 있어 재현성을 깨뜨린다. 시뮬레이션과 월드젠의 모든 수치 계산은 다음으로 제한한다.

- 기본 산술 연산(IEEE 754 `+ - * /`)
- 정수 순열 테이블 기반 밸류/Perlin 노이즈
- 고정 소수점 보간
- 정수 해시
- **32비트 정수 연산 강제**: 해시·PRNG·순열 곱셈은 `Math.imul`, `| 0`, `>>> 0` 사용 — JS 정수는 2^53을 넘으면 부정확해지므로 곱셈을 32비트로 강제한다

노이즈 스케일은 세계 좌표 기준으로 정규화한다. 같은 시드에서 지도 크기 파라미터(256/512)만 달라도 같은 세계 형태를 재현한다.

### 7.2 상태 해시 직렬화 표준

"배속이 달라도 결과가 같다"를 검증하는 상태 해시는 비결정적 요소 없이 계산되어야 한다.

- 직렬화 순서: 객체 키는 정의된 스키마 순서로 고정
- float 표현: 비트 패턴(`Float64Array` 버퍼) 또는 정규화된 문자열 형식
- 지도 레이어는 해시에서 제외(시드로 재생성 가능하므로 동일이 보장됨), 동적 상태(도시·사건·시계·원장)만 해시 대상

## 8. 집계 시뮬레이션 원칙

초기 버전에서는 개별 시민을 생성하지 않는다.

도시 단위로 다음 값을 집계한다.

- 총인구
- 연령대별 비율
- 식량 생산량
- 식량 소비량
- 재고
- 출생률
- 사망률
- 이주율
- 안정도
- 질병 수준
- 재난 피해 수준

이 방식은 성능과 구현 복잡도를 줄이면서도 의미 있는 변화를 만들 수 있다.

### 8.1 수치 안전 규칙

NaN/Infinity는 결정론 테스트를 통과하는 침묵 오염이다. 하나의 NaN이 모든 틱과 통계로 퍼진다.

- 나눗셈: 분모가 0 또는 0 미만 가능 값이면 사전 검사 후 안전값 사용
- 모든 공식 결과: 정의된 최소/최대값으로 clamp
- 불변식: 모든 상태 값(인구, 식량, 안정도 등)은 유한수여야 한다 (§33 테스트)

### 8.2 도시 상태 머신 — 폐허

인구가 0에 도달하면 도시는 **폐허(ruined)** 상태로 전환한다.

```text
  [active] ── 인구 0 도달 ──▶ [ruined]
  [ruined] ── 사용자 정착지 추가(재건) ──▶ [active]

  폐허 도시:
  - 생산/소비/이주 대상에서 제외
  - 지도에 흔적(낮은 불투명도 아이콘)으로 표시
  - 이벤트의 대상이 아님 (사전 조건에서 자동 제외)
  - 이력·통계에는 존속 (쇠퇴 스토리의 결론)
```

불가능 전환: `[ruined] → 자연 회복` (아무도 없는 도시는 스스로 살아나지 않는다). 전체 인구가 소멸해도 시뮬레이션은 계속 진행하며 통계에 기록된다.

### 8.3 인구 변화 원장 (ChangeLedger)

핵심 가치 2.1("식량 부족 47%")의 데이터 원천이다. 매 틱, 각 도시의 인구 증감을 원인별로 기록한다.

```typescript
interface PopulationChangeEntry {
  tick: number;
  settlementId: string;
  cause: "birth" | "starvation" | "disease" | "migration_in" | "migration_out" | "event";
  amount: number; // 음수 = 감소
  sourceEventId?: string; // 사건 파생 사망/출생의 근거
}
```

- 기근과 질병이 동시에 작용할 때는 정산 순서(§9.4)에 따라 단일 원인으로 귀속 — 이중 계상 금지
- 원장은 스냅샷에 포함되며 도시·기간·원인 축으로 집계 쿼리가 가능하다
- 크기: 월 1엔트리 × 도시 30 × 원인 6종 × 100년(1,200틱) ≈ 수십만 엔트리, MB 수준

# Part 4. 시간 및 시뮬레이션 엔진

## 9. 시간 단위

MVP의 기본 시뮬레이션 단위는 한 달이다.

```text
1 tick = 세계 시간 1개월
12 tick = 세계 시간 1년
```

향후 날씨나 전쟁 시스템이 필요하면 일부 시스템만 일 단위 서브 틱을 사용할 수 있다.

### 9.1 배속

기본 틱 속도: **1배속 = 2초/틱** (1년 = 24초, 100년 = 약 33분).

| 모드 | 처리 방식 |
|---|---|
| 일시 정지 | 틱 처리 없음 |
| 1배속 | 2초당 1틱 (기본값) |
| 10배속 | 초당 5틱 (0.2초/틱) |
| 100배속 | 초당 50틱 (0.02초/틱) |
| 최대 속도 | 렌더링보다 계산을 우선하여 가능한 만큼 처리 (목표 배속이 아닌 처리율 상한) |
| 1틱 진행 | 정확히 한 달 진행 |
| 1년 진행 | 정확히 12틱 진행 |

### 9.2 시스템 실행 주기와 순서 (단일 소스)

시뮬레이션 규칙의 실행 정의는 이 표 하나로 유지한다(이중 유지 금지). 매월 시스템은 §9.3의 틱 내부 순서를 따른다.

| 순서 | 시스템 | 주기 |
|---|---|---|
| §9.3.1~2 | 이벤트 지속 시간 갱신·예정 활성화 | 매월 |
| §9.3.3 | 기존 이벤트 효과 적용(수정자 스택) | 매월 |
| §9.3.4 | 기후 상태 계산 | 매월 |
| §9.3.5 | 농업 생산 계산 | 매월 |
| §9.3.6 | 식량 정산(수요·공급·재고·미충족, §9.4) | 매월 |
| §9.3.7 | 교역 계산 | 매월 |
| §9.3.8 | 인구 변화 계산(원장 기록) | 매월 |
| §9.3.9 | 이주 공동 정산(§9.6) | 매월 |
| §9.3.10 | 질병·안정도 계산 | 매월 |
| §9.3.11~14 | 사건 평가·발생·종료 | 매월 |
| 도시 성장 | 수용력 재평가 | 매년(12틱) |
| 기술 발전 | 기술 수준 갱신 | 매년 |
| 영토 변화 | 영토·지역 재조정 | 매년 |
| 장기 기후 변화 | 기후 추세 갱신 | 10년(120틱) |

주기와 순서는 시뮬레이션 규칙의 일부이므로 버전 관리한다.

### 9.3 틱 처리 순서 (매월 틱 내부)

한 틱은 다음 순서로 실행한다.

```text
1. 시간 증가
2. 예정된 이벤트 활성화
3. 기존 이벤트 효과 적용 (수정자 스택 §12.2.1)
4. 기후 상태 계산
5. 농업 생산 계산 (도시 영역 계약 §10.4 기반)
6. 식량 정산 (§9.4 단일 순서)
7. 교역 계산
8. 인구 변화 계산 (원장 §8.3 기록)
9. 이주 공동 정산 (§9.6)
10. 질병·안정도 계산
11. 사건 발생 조건 평가
12. 사건 발생 확률 계산
13. 신규 사건 생성 (통지형은 기록만, §12.4)
14. 사건 종료 처리 (수정자 pop)
15. 통계 집계
16. 이벤트 로그 저장
17. 필요 시 스냅샷 저장 (저장 큐 §28.4)
18. UI 변경 사항 전송 (쓰로틀 §9.5)
```

### 9.4 월간 식량 정산 규칙 (단일 순서)

같은 달에 기아와 교역이 충돌하지 않게 정산은 항상 다음 단방향 순서를 따른다.

```text
1. 수요 계산        — 인구 × 소비율
2. 공급 합산        — 생산 + 교역 유입 - 교역 유출
3. 재고 차감/적립   — 공급 - 수요 (부족분은 미충족으로 확정)
4. 미충족 소비 기록 — foodMonthsRemaining 갱신, 원장(F14) 귀속 준비
5. 기아 피해 적용   — 미충족 지속월数·규모에 따른 사망 (정산 후에만)
```

- 기아 사망은 미충족이 **확정된 뒤**에 적용한다 — 같은 달 도착한 교역이 주민을 구할 수 있다
- 미충족분을 재고 0 보정으로 묻지 않는다 — 부족의 크기가 원장과 이벤트 조건(§12.1)의 입력이다

### 9.5 Worker↔UI 메시지 프로토콜 (Step 5 구현 기준)

```typescript
// 요청 (UI → Worker)
type SimRequest =
  | { type: "setSpeed"; speed: 0 | 1 | 10 | 100 | "MAX" }
  | { type: "step"; ticks: 1 | 12 }
  | { type: "intervene"; intervention: UserIntervention }
  | { type: "snapshot" }
  | { type: "load"; snapshotId: string }
  | { type: "requestLLM" };

// 통지 (Worker → UI)
type SimNotification =
  | { type: "tickBatch"; fromTick: number; toTick: number; summary: WorldSummary; changes: StateChange[] }
  | { type: "majorEvent"; event: ActiveWorldEvent; paused: boolean }
  | { type: "statsUpdate"; series: StatisticsUpdate }
  | { type: "systemStatus"; level: "info" | "warning" | "error"; code: string; message: string }
  | { type: "progress"; phase: string; percent: number }; // 월드젠·로드 진행
```

- **쓰로틀**: `tickBatch`는 UI 프레임 기준 최대 초당 10회로 배치 통합 (100배속·최대 속도에서 폭주 방지)
- **자동 일시 정지**: 중요도 임계 초과 사건은 즉시 `majorEvent` 통지 + Worker가 자체 정지. UI 응답 전 추가 틱 없음
- **오류 노출**: 저장 실패·템플릿 격리·LLM 폴밋은 모두 `systemStatus`로 사용자에게 보인다 (§22.1)
- **버퍼 전달**: 지도 레이어 등 대용량 `TypedArray`는 구조적 복사가 아니라 **transfer list로 전달**(제로카피)한다. 월드젠 코드는 Worker 단일 소스 — UI는 렌더링만 담당하고 지도 생성 코드를 갖지 않는다 (결정론 단일 소스, §31)

### 9.6 이주 공동 정산 규칙

같은 달의 동시 이주가 처리 순서에 의존하지 않게 한다.

```text
1. 월초 인구 스냅샷 기준으로 모든 도시의 이주 압력·희망 이동량 산정
2. 목적지별 신청 합산 → 수용력 초과 시 신청 비율 배분 (비례 축소)
3. 확정된 이동만 적용 — 도착 인구는 같은 달 재이동 금지
4. 불변식: 출발 감소 총합 = 도착 증가 총합 (세계 총인구 보존, §33)
```

- 산정과 적용의 2단계 분리로 도시 처리 순서가 결과에 영향주지 않는다
- 배분 비율 계산에도 §8.1 수치 안전 규칙(분모 0 검사·clamp)을 적용한다

### 12.2.1 효과 적용 모델 — 수정자 스택

효과가 기준값을 덮어쓰거나 매달 복리로 누적하지 않게 한다. 모든 메트릭은 "기준값 + 활성 수정자 스택"으로 계산한다.

```text
metric = clamp(base × Π(modifiers), minimum, maximum)

base       = 이벤트가 없을 때의 값 (환경·시설에서 계산)
modifiers  = 활성 이벤트의 곱셈 수정자들 (0.65 등)
add 효과   = base 자체에 한 번 적용 (영구 변경 — 예: 자원 발견)
```

- 이벤트 시작: 수정자를 스택에 push. 종료: pop — 원복이 자동 보장
- 같은 이벤트의 중첩: `maximumConcurrentInstances`가 1로 제한하므로 발생하지 않는다
- add(영구)와 multiply(기간 한정)를 명확히 구분하며, 템플릿 작성 시 하나의 효과는 둘 중 하나만 사용한다

### 12.3 후속 사건

```typescript
interface FollowUpCandidate {
  eventTemplateId: string;
  minimumDelayTicks: number;
  maximumDelayTicks: number;
  baseWeight: number;
  conditions: EventCondition[];
}
```

### 12.4 이벤트 유형 — 통지형 vs 효과형

기본 시스템이 이미 계산하는 변화를 사건 효과로 다시 적용하는 **이중 적용을 금지**한다. 모든 템플릿은 둘 중 하나로 분류한다 (`EventTemplate.kind`).

| 유형 | 의미 | 예 | 효과 제한 |
|---|---|---|---|
| `notification` (통지형) | 기본 시스템 계산 결과를 사건으로 기록·알림만 | 도시 성장, 도시 쇠퇴, 대규모 이주 | `immediateEffects`·`ongoingEffects` 금지 — 원장 귀속용 `sourceEventId`만 생성 |
| `effect` (효과형) | 수정자 스택으로 실제 상태 변화를 추가 | 가뭄, 홍수, 전염병, 폭동 | §12.2.1 수정자 스택 필수, §20 수치 범위 준수 |

- 통지형의 발생 판정은 기본 계산 결과가 임계값을 넘는지로 대체한다 (예: 순이주 ≥ 인구의 5% → "대규모 이주" 통지)
- 통지형은 원장(§8.3)의 원인 라벨을 풍부하게 만들 뿐 수치를 바꾸지 않는다

## 13. 사건 발생 확률

LLM은 사건 발생 확률을 직접 결정하지 않는다.

시뮬레이션 엔진은 다음 요소로 사건 확률을 계산한다.

- 기본 확률
- 조건 충족 정도
- 현재 도시 상태
- 선행 사건
- 계절
- 지역 특성
- 중복 사건 감쇠
- 최근 동일 사건 발생 여부
- 사용자 정책
- 난이도 및 세계 설정

개념적인 확률은 다음과 같이 구성한다.

$$
P(E)=\operatorname{clamp}
\left(
P_{\mathrm{base}}
\times M_{\mathrm{condition}}
\times M_{\mathrm{chain}}
\times M_{\mathrm{environment}}
\times M_{\mathrm{policy}}
\times M_{\mathrm{cooldown}},
0,
P_{\mathrm{max}}
\right)
$$

예를 들어 식량 폭동은 다음 조건의 영향을 받을 수 있다.

- 식량 재고가 적을수록 확률 증가
- 식량 가격이 높을수록 확률 증가
- 안정도가 낮을수록 확률 증가
- 최근 가뭄이 있었다면 확률 증가
- 식량 지원 정책이 있으면 확률 감소
- 최근 폭동이 종료됐다면 재발 확률 감소

### 13.1 확률 평가 결과

UI와 디버깅을 위해 확률 계산 근거를 보존한다.

```typescript
interface ProbabilityEvaluation {
  eventTemplateId: string;
  targetId: string;
  tick: number;

  baseProbability: number;
  modifiers: ProbabilityModifier[];
  finalProbability: number;

  randomValue: number;
  occurred: boolean;
}
```

```typescript
interface ProbabilityModifier {
  source: string;
  value: number;
  explanation: string;
}
```

예:

```text
식량 폭동 발생 확률: 31.8%

기본 확률                  2.0%
식량 재고 1개월 이하      × 3.2
식량 가격 급등             × 2.1
안정도 40 이하             × 1.8
최근 가뭄 발생             × 1.4
식량 지원 정책             × 0.6
```

## 14. 연쇄 사건

사건은 다른 사건의 후보를 생성할 수 있다.

예:

```text
가뭄
  ├── 흉년
  │    ├── 식량 가격 상승
  │    │    ├── 식량 폭동
  │    │    └── 밀수 증가
  │    └── 영양실조
  │         └── 전염병 취약성 증가
  ├── 강 유량 감소
  │    ├── 물 부족
  │    └── 수력 생산 감소
  └── 대규모 이주
       ├── 인접 도시 인구 증가
       ├── 주거 부족
       └── 지역 갈등
```

연쇄 사건은 무조건 발생하지 않는다.

선행 사건은 다음 사건의 후보와 확률 보정값만 만든다.

```text
선행 사건 발생
    ↓
후속 사건 후보 등록
    ↓
최소 지연 시간 경과
    ↓
현재 상태 조건 확인
    ↓
발생 확률 계산
    ↓
결정론적 난수 판정
    ↓
발생 또는 후보 만료
```

### 14.1 무한 연쇄 방지

- 이벤트별 최대 깊이 제한
- 동일 이벤트의 재발 쿨다운
- 하나의 원인 사건이 생성할 수 있는 후보 수 제한
- 세계 전체 동시 활성 이벤트 수 제한
- 도시별 동시 활성 이벤트 수 제한
- 낮은 영향도의 반복 사건 통합
- 순환 이벤트 탐지
- 후속 후보 만료 시간 설정

MVP 권장값:

```text
최대 연쇄 깊이: 4
원인 사건당 후속 후보: 최대 5개
도시별 활성 사건: 최대 3개
세계 전체 중요 사건: 최대 20개
동일 사건 쿨다운: 최소 12틱
```

# Part 7. LLM 기반 동적 이벤트

## 15. LLM 기능의 목적

규칙 기반 이벤트만 사용하면 안정적이지만 반복적으로 느껴질 수 있다.

LLM은 현재 세계 상태와 최근 역사를 바탕으로 다음을 제안한다.

- 상황에 맞는 사건 후보
- 기존 사건에서 파생되는 연쇄 사건
- 세계관에 맞는 사건명
- 사건 설명
- 사용자 개입 선택지
- 사건의 역사적 요약
- 예상하지 못한 복합 사건

예:

```text
현재 상태
- 3년 연속 가뭄
- 북부 도시의 식량 재고 1.2개월
- 남부 도시는 곡물 잉여
- 북부와 남부를 잇는 도로가 홍수로 단절
- 북부 도시 안정도 38

LLM 추천 후보
1. 곡물 운송대 습격
2. 북부 식량 배급제 도입
3. 암시장 형성
4. 남부 상인의 긴급 해상 교역
5. 북부 주민의 대규모 남하
```

## 16. LLM 이벤트 생성 절차

```text
1. 시뮬레이션 엔진이 중요 상태 변화 감지
2. LLM 호출 필요 여부 판단
3. 세계 상태를 요약
4. 허용된 메트릭과 이벤트 DSL 제공
5. LLM이 사건 후보 3~5개 반환
6. JSON 스키마 검증
7. 허용된 조건과 효과인지 검증
8. 수치 범위 검증
9. 기존 사건과 중복 여부 확인
10. 위험도 및 균형 검증
11. 사용자에게 후보 표시
12. 자동 승인 또는 수동 승인
13. 승인된 후보를 이벤트 템플릿으로 등록
14. 규칙 엔진이 실제 발생 확률 계산
15. 발생 여부를 결정론적으로 판정
```

## 17. LLM 호출 조건

LLM을 매 틱 호출하지 않는다.

다음 상황에서만 호출한다.

- 사용자가 직접 추천을 요청
- 중요 사건이 발생
- 일정 기간 동안 주요 사건이 없음
- 세계 상태가 이전에 없던 임계값 조합에 도달
- 새로운 연쇄 사건 후보가 부족
- 사용자가 특정 도시나 지역의 미래 가능성을 요청
- 세계 시간으로 일정 기간마다 역사 요약 생성

MVP 권장 호출 조건:

```text
수동 추천 요청
또는
세계 시간 5년마다 최대 1회
또는
중요도 80 이상의 사건 발생 직후
```

## 19. LLM 출력 형식

LLM은 반드시 구조화된 JSON을 반환한다.

```json
{
  "recommendations": [
    {
      "temporaryId": "candidate_1",
      "name": "북부 곡물 암시장",
      "category": "economic",
      "summary": "공식 배급망이 부족해지면서 비공식 곡물 거래가 확산됩니다.",
      "scope": "settlement",
      "targetIds": ["aren"],
      "preconditions": [
        {
          "metric": "settlement.foodMonthsRemaining",
          "operator": "lt",
          "value": 2
        },
        {
          "metric": "settlement.stability",
          "operator": "lt",
          "value": 50
        }
      ],
      "suggestedBaseProbability": 0.08,
      "suggestedDurationTicks": 8,
      "effects": [
        {
          "targetMetric": "settlement.foodPriceIndex",
          "operation": "multiply",
          "value": 1.12
        },
        {
          "targetMetric": "settlement.stability",
          "operation": "add",
          "value": -2
        }
      ],
      "followUps": [
        {
          "eventType": "smuggling_crackdown",
          "minimumDelayTicks": 2,
          "maximumDelayTicks": 6,
          "baseWeight": 0.4
        }
      ],
      "reasoningSummary": "식량 부족과 낮은 안정도가 암시장 형성 조건을 충족합니다."
    }
  ]
}
```

`suggestedBaseProbability`는 참고값이다.

최종 기본 확률은 다음 중 하나로 결정한다.

1. 기존 이벤트 카테고리의 기본값 사용
2. 서버 또는 클라이언트의 안전 범위로 제한
3. 사용자 승인
4. 이벤트 밸런스 정책 적용

## 20. LLM 이벤트 검증 규칙

### 20.1 스키마 검증

- 필수 필드 확인
- 올바른 데이터 타입 확인
- 알 수 없는 필드 제거
- 문자열 길이 제한
- 후보 개수 제한

### 20.2 메트릭 검증

LLM이 수정할 수 있는 메트릭은 허용 목록으로 제한한다.

예:

```text
허용
- settlement.foodProduction
- settlement.foodStock
- settlement.stability
- settlement.migrationPressure
- settlement.diseaseLevel
- route.capacity

금지
- world.seed
- world.simulationVersion
- settlement.id
- eventHistory
- arbitraryCode
```

### 20.3 수치 검증

예:

| 효과 | 한 사건에서 허용 범위 |
|---|---:|
| 식량 생산 배율 | 0.5~1.5 |
| 안정도 변화 | -15~15 |
| 질병 수준 변화 | -0.2~0.2 |
| 이주 압력 변화 | -0.3~0.3 |
| 교역로 용량 배율 | 0.3~1.5 |
| 사건 지속 시간 | 1~36틱 |

범위를 벗어나면 다음 중 하나로 처리한다.

- 안전 범위로 보정
- 후보 거부
- 사용자에게 수정 요청
- 규칙 기반 기본값으로 대체

### 20.4 의미 검증

- 현재 존재하는 도시와 지역만 참조하는가?
- 사전 조건과 효과가 모순되지 않는가?
- 이미 활성화된 사건과 중복되지 않는가?
- 사건이 현재 세계관과 맞는가?
- 존재하지 않는 기술이나 자원을 요구하지 않는가?
- 연쇄 깊이 제한을 초과하지 않는가?

## 21. LLM 운영 모드

### 21.1 추천 전용 모드

- LLM이 후보를 표시한다.
- 사용자가 하나를 선택한다.
- 선택된 후보만 검증 및 등록한다.

초기 버전에서 권장한다.

### 21.2 반자동 모드

- 안전 등급이 높은 사건은 자동 등록한다.
- 영향이 큰 사건은 사용자 승인을 요구한다.

예:

```text
낮은 영향: 자동 승인 가능
중간 영향: 설정에 따라 자동 승인
높은 영향: 항상 수동 승인
```

### 21.3 완전 자동 모드

- 검증을 통과한 후보가 자동 등록된다.
- 실제 발생 여부는 시뮬레이션 엔진이 결정한다.
- 중요 사건 발생 시 사용자에게 알린다.

MVP 이후에 추가한다.

## 22. LLM 실패 대응

다음 상황에서 규칙 기반 시스템으로 대체한다.

- API 호출 실패
- 응답 시간 초과
- JSON 파싱 실패
- 스키마 검증 실패
- 허용되지 않은 효과 반환
- 중복 후보만 반환
- 비용 제한 도달
- 네트워크 연결 없음

LLM이 없어도 시뮬레이션은 정상적으로 진행되어야 한다.

```text
LLM 사용 가능 → 동적 사건 추천
LLM 사용 불가 → 내장 이벤트 템플릿 사용
```

### 22.1 엔진 내부 오류 분류·격리

LLM 실패 대응과 대칭되는 내장 경로 대응. 한 템플릿의 버그가 전체 시뮬레이션을 죽이지 않는다.

| 오류 | 원인 | 격리 동작 | 사용자 노출 |
|---|---|---|---|
| `UnknownMetricError` | 템플릿이 허용 목록 밖 메트릭 참조 | 해당 템플릿 비활성화 + 경고 로그, 시뮬 계속 | systemStatus 배너 "사건 X 비활성화됨" |
| `InvalidTemplateError` | 스키마·범위 위반 (내장/LLM 공통) | 등록 거부, 나머지 템플릿 정상 | systemStatus 경고 |
| `InvalidEffectTarget` | 존재하지 않는 도시/루트 참조 | 해당 인스턴스 건너뜀, 원장에 기록 | 디버그 패널 |
| `SnapshotQuotaError` | IndexedDB 용량 초과 | 오래된 자동 스냅샷 정리 후 재시도, 실패 시 저장 중단 | 배너 "저장 공간 부족" |
| `SnapshotCorruptError` | 로드 데이터 손상/버전 불일치 | 로드 거부 + 안내 (§28.3) | 대화상자 "버전이 달라 열 수 없음" |

모든 오류는 원인·틱·대상을 포함한 구조화 로그로 남는다 ("swallow and continue" 금지 — 경고가 보여야 계속하는 것).

## 23. LLM 결과 재현성

외부 LLM은 동일한 입력에서도 다른 결과를 반환할 수 있다.

따라서 승인된 LLM 결과를 그대로 저장한다.

```typescript
interface LLMGenerationRecord {
  id: string;
  createdAtTick: number;

  provider: string;
  model: string;
  promptVersion: string;

  inputHash: string;
  rawOutput: string;
  parsedOutput: unknown;
  validatedEventTemplateIds: string[];

  approvedBy: "user" | "automatic";

  // 재현성 보강 — 승인이 언제 어디에 적용됐는지
  appliedAtTick: number;        // 실제 확률 평가에 참여 시작 틱
  branchId: string;             // 등록된 분기
  registrationOrder: number;    // 같은 틱 내 등록 순서
  requestSnapshotId: string;    // 요청 시점 상태 스냅샷 (늦은 응답 판정 기준)
}
```

늦은 응답 규칙: 요청 시점 스냅샷과 현재 상태의 해시가 다르면(시간이 흘렀거나 분기가 바뀌면) 응답은 폐기하고 재요청한다. 같은 출력이 다른 틱·분기에서 다른 결과를 내는 것을 방지한다.

재실행 시 LLM을 다시 호출하지 않고 저장된 결과를 사용한다.

분기 시뮬레이션에서는 다음 옵션을 제공한다.

- 기존 LLM 결과 재사용
- 새로운 후보 다시 생성
- LLM 없이 규칙 기반 사건만 사용

### 레이아웃 수치

```text
┌──────────────────────────────────────────────────────────┐
│ 상단 48px  정체성·시간 제어 (아래)                        │
├────────┬──────────────────────────────┬──────────────────┤
│ 좌 280px│      중앙 flex (지도 최소 55%) │  우 360px        │
│ (접기 가능)│                              │ (컨텍스트 패널)   │
├────────┴──────────────────────────────┴──────────────────┤
│ 하단 200px 타임라인(마스터) + 탭 차트(인구/식량/안정도)      │
└──────────────────────────────────────────────────────────┘
좌우 패널 접기 시 지도가 공간을 흡수. 최소 지원 창 1280×800.
```

### 상단 — 역할별 그룹화

```text
[World Observatory · 세계명 · 관찰 모드] | [세계력 142년 3월] | [▶/⏸ 재생·정지]
[속도: 1x 10x 100x MAX] [단계 진행: 1개월 ▸ / 1년 ▸▸] [저장 상태: 마지막 저장 3분 전]
```

- 정체성 표기가 첫 화면에서 제품을 알린다 (리트머스 #1)
- '1틱 진행'은 실제 단위를 드러내는 **'1개월 진행'**으로 표기. '1년 진행'은 단계 진행 그룹에
- 저장은 수동 버튼 + 마지막 저장 시각 라벨 (자동 저장은 §28.4 큐, 상태만 표시)

### 왼쪽 — 큐레이션 사이드바

- 기본 펼침: **도시 목록** (위기순 정렬 — 식량 재고 개월 수 오름차순, 같으면 안정도 낮은 순)
- 접힘(필요 시 열기): 지도 레이어(§26), 세계 통계, 이벤트 필터
- 검색: 사이드바 상단 고정 인풋

### 중앙 — 지도 (화면의 주인공)

세계 지도·도시·강·도로·이주 애니메이션·사건 아이콘. 최소 55% 보장.

### 오른쪽 — 컨텍스트 소유 모델

**선택 객체(도시/사건/없음) 하나가 패널 전체를 소유한다.** 6개 관심사의 병렬 배치는 금지.

```text
선택 없음     → 활성 사건 요약 + 세계 헤드라인 (디폴트)
사건 선택     → §27 사건 상세 (원인 → 영향 → 조건부 확률 → 개입)
도시 선택     → §27.4 도시 상세 (요약 → 원인 분해 → 시계열)
패널 하단     → 항상 노출 고정 액션 영역: LLM 추천 요청 · 개입 (§27.6)
```

### 하단 — 타임라인 마스터 + 탭 차트

- 역사 타임라인(마스터) — 이벤트 로그는 타임라인의 **리스트 뷰**(같은 데이터의 다른 표현)로 통합
- 차트 3종(인구/식량/안정도)은 탭 전환. 이벤트 필터는 타임라인·리스트 양쪽에 적용
- 스냅샷 마커 클릭 → 과거 열람 모드 배지("과거 기록 열람 중") + **[이 시점에서 분기]** 버튼 → 분기 비교 오버레이

### Watch Mode (Step 10 완료 조건의 정의)

- 진입: 시간 제어 옆 토글. 동작: "다음 중요 사건"까지 자동 재생 → 자동 정지 → 카메라 이동 → 상세 패널 open → 반복
- 종료: 토글 해제. 자동 정지 시 사유 배지 표시: **"사건 정지: 대가뭄" / "수동"** — 갑자기 멈춘 화면의 고장 오인 방지
- 자동 정지 임계값(중요도)은 설정에서 조절 가능

## 26. 지도 레이어 — 계층 모델과 색 유형

14개 레이어를 3계층으로 재구성한다.

```text
L0 베이스 (택 1):    기본 지형 | 바이옴 | 고도 | 온도 | 습도
L1 데이터 오버레이 (최대 2): 식량 생산성, 물 공급, 인구 밀도, 식량 부족,
                            안정도, 질병, 교역 (반투명 겹침)
상시 오버레이 (항상): 활성 사건 아이콘, 이주 흐름, 선택 강조
```

### 색 유형 규칙 (의미 반전 방지)

| 레이어 성격 | 색 유형 | 예시 |
|---|---|---|
| 위험·부족 (높을수록 나쁨) | **발산형** (안전→위험) | 식량 부족, 질병, 안정도(역) |
| 양적·풍요 (높을수록 좋음) | **순차형** (단색 그라데이션) | 식량 생산성, 물 공급 |
| 환경 (범주) | 범주형 팔레트 | 바이옴 |

- 모든 팔레트는 **색약 안전(Viridis/Cividis 계열)** — §27.8 접근성 전제
- 주제 레이어(L1)마다 단위·범위·기준 시점이 있는 범례를 지도 하단에 표시
- 선택 도시·선택 사건 강조는 모든 레이어 조합에서 동일 방식(링 + 라벨)

```text
중요도: 매우 높음
예상 지속 기간: 18개월

발생 원인
- 최근 24개월 평균 강수량 42%
- 평균 기온 편차 +1.8
- 토양 수분 31%

직접 영향
- 농업 생산량 -35%

```

> §27의 "예상 후속 사건" 확률은 **현재 상태 기준 조건부 확률**(§2.2)이다. 라벨에 그렇게 표기한다.

## 27.1 시스템 상태 표시 규격

관찰 도구가 자기 문제를 침묵시키지 않는다. 모든 시스템 문제는 다음 두 계층으로 노출된다.

**상단 상태 배너** (`systemStatus`, §9.5):

| 코드 | 표시 | 예 |
|---|---|---|
| info | 접힌 상태 표시기 | LLM 폴백 모드로 실행 중 |
| warning | 노란 배너 | 사건 템플릿 X 비활성화됨 (UnknownMetricError) |
| error | 빨간 배너 + 저장 중단 | 저장 공간 부족 — 스냅샷 정리 필요 |

**개발용 디버그 패널** (토글): 틱당 소요 시간, 활성 템플릿 수, 격리된 템플릿 목록, 구조화 오류 로그, 시드/버전 요약.

## 27.2 인터랙션 상태 커버리지 맵

| 기능 | LOADING | EMPTY | ERROR | SUCCESS | PARTIAL |
|---|---|---|---|---|---|
| 세계 생성 | 단계별 진행 표시 (`progress`) | — (불가) | 품질 재생성 중 표시 (§28 재생성) | 지도 등장 + 도시 순차 점등 | — |
| 지도 | 지도 재생성 진행 | 도시 0개(재생성됨) | 렌더 오류 시 재시도 배너 | — | 폐허는 흔적 표시 |
| 사건 타임라인 | 대량 이력 로드 시 스로틀 표시 | "아직 사건이 없습니다 — 시간을 진행하세요" | — | — | 필터 결과 0건 안내 |
| 도시 상세(우측 패널) | — (불가) | "도시를 클릭하면 상세가 나타납니다" | — | §27.4 렌더 | 폐허는 §27.5 |
| 통계 차트(하단 탭) | — | "기록이 없습니다 — 시간을 진행하면 채워집니다" | — | — | 시간축 부분 구간 |
| 개입 실행 | 적용 중 (짧음) | — (불가) | 적용 실패 배너 + 재시도 | "적용됨 — 다음 틱부터 반영, 원장에 기록됨" (§27.6) | — |
| 저장 | 저장 중 (수동 버튼) | 저장된 세계 없음: "새 세계를 만들어보세요" | 버전 불일치 대화상자 (§28.6) | 마지막 저장 시각 라벨 갱신 | — |
| LLM 추천 패널 | 요청 중 표시 | "LLM 키 미설정 — 설정에서 입력" | §22 폴백 안내 | 후보 등록 확인 (승인 후) | 후보 0건: "지금 상태엔 제안이 없음" |
| 분기 비교 | 두 분기 로드 중 | "비교할 다른 분기가 없습니다 — 과거 시점에서 분기를 만들어보세요" | — | 차이 수치 표시 | 부분 구간만 겹칠 때 안내 |

- "—"는 **원천 불가능**, 별도 표기 없는 칸은 **미정(TODO)**으로 구분한다
- **배너 스태킹 규칙**: 동시 다발 시 심각도순(error→warning→info) 최대 3개 노출, 나머지는 "외 N건" 집계 배지로 접기

## 27.3 첫 5분 온보딩 스토리보드 — 데드 타임 대응 포함

```text
[새 세계] 클릭
  → 랜덤 시드 자동 생성, 생성 단계 진행 표시 (2~5초)
  → 지도 등장 + 도시 하이라이트 순차 점등
  → 하단 안내: "▶ 버튼으로 시간을 진행해보세요" (1회성)
  → [시간 진행 중] 살아있음 피드백: 도시 라벨 인구 숫자 갱신, 계절 표시 전환,
    이주 애니메이션, 소소한 통지 흐름("정착지 안정") — 화면이 멈춰 보이지 않게
  → 첫 사건 발생 (튜토리얼 세계 한정: 첫 12틱 내 사건 1건 강제 시딩 —
    WorldConfig.tutorialWorld 플래그, §33 평상시 밸런스 시나리오와 분리)
  → 자동 일시 정지 + 안내 배지 "첫 사건을 살펴보기 위해 일시 정지했습니다" + [계속 관찰]
  → 사건 상세 패널 열림: 원인 · 직접 영향 · 가능한 개입 (§27 형식)
  → 사용자는 개입하거나 계속 관찰 — 두 경로 모두 5분 안에 도달
```

온보딩 강제 없음: 안내는 1회성이며 모든 기능은 탐색으로도 발견 가능해야 한다. 모션 줄이기 설정이 온보딩 모션(순차 점등·이주 애니메이션)에도 적용된다.

## 27.6 개입 피드백 루프 (개입 → 추적 → 회기)

```text
개입 선택 → 확정 → 확인: "적용됨 — 다음 틱부터 반영, 원장에 기록됨"
  → 도시·사건 상세에 [개입 후 N개월] 배지
  → [이 개입의 효과 보기] 링크 → 분기 비교 오버레이
  → 회기 예: "당신의 개입으로 이후 10년 사망자가 원본 대비 -62%" (§2.3 완성)
```

## 27.7 기능 언어·수치 해석 규칙

- 모든 수치는 **기준과 단위를 동반**: "최근 24개월 강수량: 평년 대비 42%", "평균 기온 편차: +1.8°C"
- 확률 표기: "현재 상태 기준 이번 달 조건부 확률" + 산출 시점. 사건별 확률이 배타적이지 않음을 명시
- 개입 버튼: 적용 대상·비용(있을 때)·예상 효과 방향 표기. 관찰 유지 선택은 **"개입 없이 계속 관찰"**로 명시
- 오류 문구 3단 구조: **문제 → 관찰에 미치는 영향 → 복구 행동** (예: "일부 사건 계산이 중단되었습니다 · 다른 시뮬레이션은 계속됩니다 · 상세 보기"). 오류 코드는 디버그 패널로
- 자동 재생성: 횟수 표시("지도 재구성 중 2/5"), 최종 실패 시 안내 화면

## 27.8 접근성 기준

- 본문 텍스트 대비 4.5:1 이상, 히트맵·아이콘 팔레트는 색약 안전(Viridis/Cividis 계열) — §26 색 유형의 전제
- 키보드 탐색: Tab 순서 = 좌 사이드바 → 중앙 지도 → 우측 패널 → 하단. 도시 목록·타임라인은 방향키 탐색, Enter 선택
- 터치·클릭 타깃 최소 44px. 모션 줄이기 설정(애니메이션 전반, 온보딩 포함)

- 1년마다 자동 스냅샷
- 중요 사건 발생 직전 선택적 스냅샷
- 최근 100년 유지
- 사용자가 지정한 스냅샷은 자동 삭제하지 않음

### 28.3 스냅샷 내용 — 지도 제외, 동적 상태만

지도 레이어 6종 × 512×512 ≈ 6.3MB다. 지도를 스냅샷에 포함하면 100년치(100스냅샷)가 약 630MB로 브라우저 IndexedDB 한도를 넘는다. 지도는 결정론상 불변이므로 저장하지 않는다.

```text
스냅샷 = {
  seed, generatorVersion, simulationVersion, worldConfig  (지도 재생성 입력)
  clock, settlements, routes                              (동적 상태)
  activeEvents, scheduledEvents, modifierStacks            (이벤트 상태)
  changeLedger (증분)                                     (§8.3 원장)
  statistics (증분)
}
크기: 도시 30개 기준 수십 KB — 100년 유지 정책을 그대로 지킨다
```

로드 시: 시드로 지도를 재생성(1~3초, `progress` 통지로 진행 표시)한 뒤 동적 상태를 덮어쓴다.

### 28.4 저장 실행 — Worker 내 저장 큐

- 저장은 Worker 내부의 저장 큐에서 비동기 처리한다 (틱 루프와 인터리브하지 않음)
- 틱 사이 배치로 flush — "스냅샷 저장으로 장시간 정지가 발생하지 않음"(§34)의 메커니즘
- 세계는 랜덤 생성 시드에서 시작하고 시드는 생성 즉시 저장소에 보관된다 (사용자 시드 입력은 재현·공유용 선택 기능)

### 28.5 용량 정책

- 자동 스냅샷은 §28.2 유지 정책에 따라 오래된 것부터 정리한다 (사용자 지정 보호)
- `SnapshotQuotaError`(용량 초과) 시: 정리 → 재시도 → 실패 시 저장 중단 + 배너 알림 (§22.1)

### 28.6 저장 포맷 버전 정책

- 저장 데이터는 `simulationVersion`과 정확히 일치할 때만 로드한다
- 불일치 시 로드 거부 + "이 세계는 버전 X에서 만들어졌다" 안내
- 마이그레이션은 필요해진 시점에 명시적으로 작성한다 (기본은 새 세계 생성)

# Part 12. 품질 및 테스트 전략

## 33. 필수 테스트

### 결정론 테스트

- 같은 시드에서 같은 세계가 생성되는가?
- 같은 입력으로 같은 사건이 발생하는가?
- 배속이 달라도 최종 결과가 같은가?
- 저장 후 불러온 결과가 원본과 같은가?
- 스냅샷 재생 결과가 직접 실행 결과와 같은가?

### 시뮬레이션 불변식 테스트

- 인구는 음수가 되지 않는다.
- 식량 재고는 정책상 허용하지 않는 한 음수가 되지 않는다.
- 확률은 0과 1 사이에 있다.
- 존재하지 않는 도시로 이주하지 않는다.
- 종료된 사건의 지속 효과가 남지 않는다.
- 하나의 도시가 지도 밖에 위치하지 않는다.
- 도시 간 이동 인구의 총합이 보존된다.

### 이벤트 테스트

- 조건을 만족하지 않으면 사건이 발생하지 않는다.
- 조건을 만족하면 확률 평가 대상이 된다.
- 쿨다운 중인 사건은 재발하지 않는다.
- 연쇄 깊이 제한이 적용된다.
- 동일 사건이 과도하게 중첩되지 않는다.
- 후속 사건 후보가 정해진 기간 후 만료된다.

### LLM 테스트

- 잘못된 JSON을 거부하는가?
- 알 수 없는 메트릭을 거부하는가?
- 허용 범위를 벗어난 효과를 거부하거나 보정하는가?
- 존재하지 않는 도시 참조를 거부하는가?
- LLM 실패 시 기본 이벤트로 대체하는가?
- 저장된 LLM 결과를 재실행할 때 재사용하는가?
- 늦게 도착한 응답이 요청 시점 스냅샷 불일치 시 폐기되는가? (§23)

### 수치 안전·상태 불변식 (확장)

- 모든 상태 값은 유한수다 (NaN/±Infinity 금지 — §8.1)
- 인구 0 도달 시 폐허 전환, 폐허 도시는 생산·이주·이벤트 대상에서 제외된다 (§8.2)
- 이벤트 종료 후 수정자 스택이 원복된다 (메트릭 = base × Π(modifiers), §12.2.1)
- 인구 변화 원장의 원인별 합이 총 인구 변화와 일치한다 (§8.3)
- 같은 달 미충족 식량이 확정된 뒤에만 기아 사망이 적용된다 (§9.4)

### 밸런스 시나리오 테스트 (고정 시나리오)

결정론 테스트는 결과 일치만 확인한다. 세계가 "살아 있는지"는 다음 3종 고정 시나리오가 검증한다.

1. **평상시 유지**: 개입 없이 50년 — 도시 멸망·폭발 성장 없이 평형 유지
2. **흉작 후 회복**: 가뭄 3년 — 인구 감소 후 재고 회복과 인구 안정화
3. **교역 단절 전파**: 북부 가뭄 + 남북 도로 단절 — 기아 발생, 재개 후 회복

실행 기준: 도시 2개·가뭄 1개·24틱의 손계산 예시(worked example)를 문서로 먼저 작성하고, 시나리오 테스트가 이 예시와 일치하는지 검증한다. 공식 수정 시 예시를 다시 계산한다.

### 성능 벤치마크 테스트

- 기준 세계(512×512, 도시 30, 활성 이벤트 20 이하)에서 1,200틱(100년) 실행 시간이 상한 이내인지 측정
- 틱당 평균 소요 시간과 p99를 기록해 회귀 감지 (성능 목표 §34의 검증 수단)

### UI 검증 (E2E / 수동 체크리스트)

- 사건 상세 패널에 확률 계산 근거가 표시되는가 (Playwright)
- 인구 감소 원인 분해(§2.1)가 도시 상세에 표시되는가
- 폐허 도시가 지도에 흔적으로 표시되고 클릭 시 이력을 보여주는가
- 시스템 상태 배너(저장 실패·격리·폴백)가 조건 발생 시 나타나는가
- 분기 비교 화면이 두 역사의 차이를 수치로 보여주는가

# Part 15. 우선순위 및 개발 규칙

## 35. 우선순위

1. 결정론
2. 시뮬레이션 상태의 정확성
3. 사건의 인과관계
4. 관찰 가능성
5. 저장과 재현
6. LLM 추천
7. 그래픽 완성도
8. 추가 콘텐츠 양

> **확정 (2026-09-17, 리뷰 F-참고 해소)**: 표는 엔지니어링 트레이드오프 판정 규칙(제약 순서)으로 현행 유지. 제품 가치 순서는 §2(3대 질문)가 담당한다. 관찰 가능성은 인구 변화 원장(§8.3)·확률 평가 기록(§13.1)·상태 표시 규격(§27.1) 도입으로 구조적으로 강화됐다.

LLM 기능은 이벤트 엔진이 완성된 후 추가한다.

이벤트 엔진보다 LLM을 먼저 만들면 다음 문제가 생길 수 있다.

- LLM 출력이 상태를 임의로 변경
- 결과 재현 불가
- 사건 밸런스 붕괴
- 실패 원인 추적 불가
- API가 없으면 프로젝트 실행 불가

---

## 36. Step 진행 규칙

각 Step은 다음 순서로 진행한다.

1. 목표를 한 문장으로 정의한다.
2. 입력과 출력을 정의한다.
3. 데이터 타입을 먼저 작성한다.
4. 실패 조건을 정의한다.
5. 핵심 로직의 테스트를 작성한다.
6. 최소 구현을 작성한다.
7. 디버그 화면을 추가한다.
8. 성능을 측정한다.
9. 완료 조건을 확인한다.
10. 다음 Step으로 넘어간다.

완료 조건을 충족하지 않은 상태에서 다음 Step의 기능을 섞지 않는다.

---

## 37. 바이브코딩 작업 단위

LLM에는 전체 Step을 한 번에 구현하도록 요청하지 않는다.

좋은 작업 단위 예:

```text
WorldMap의 TypedArray 데이터 모델만 작성해줘.
렌더링과 생성 로직은 포함하지 마.
```

```text
동일한 시드에서 동일한 값을 반환하는 PRNG와 Vitest 테스트를 작성해줘.
Math.random은 사용하지 마.
```

```text
EventCondition 배열을 평가하는 순수 함수를 작성해줘.
지원하지 않는 메트릭은 오류를 반환하게 해줘.
```

```text
1배속과 100배속으로 1,200틱을 실행했을 때 상태 해시가 같은지 검증하는 테스트를 작성해줘.
```

```text
LLM 이벤트 JSON을 Zod로 검증하되 허용 메트릭 목록에 없는 효과는 거부하도록 작성해줘.
```

7. 남부 도시의 주거 및 식량 부담 증가
8. LLM이 다음 후보를 추천
   - 북부 식량 배급제
   - 곡물 암시장
   - 남부 긴급 해상 교역
   - 난민 수용 갈등
   - 관개 기술 투자
9. 사용자가 하나의 정책을 선택
10. 10년 후 결과 비교

### 성공 기준

사용자가 다음 내용을 이해할 수 있어야 한다.

- 왜 북부 인구가 감소했는가?
- 어떤 경로로 사람들이 이동했는가?
- 남부 도시에는 어떤 부작용이 생겼는가?
- 다음에 어떤 사건이 발생할 가능성이 있는가?
- 식량 지원이 없었을 때와 있었을 때 결과가 어떻게 다른가?

# Part 17. 최종 완료 정의

프로젝트의 첫 번째 주요 버전은 다음 조건을 만족하면 완료로 간주한다.

- 시드 기반 세계 생성이 재현된다.
- 도시가 환경에 따라 성장하고 쇠퇴한다.
- 시간 배속이 결과에 영향을 주지 않는다.
- 식량, 인구, 안정도, 이주가 연결되어 있다.
- 자연 사건과 사회 사건이 연쇄적으로 발생한다.
- 사건의 발생 확률과 근거를 볼 수 있다.
- LLM이 현재 상황에 맞는 사건 후보를 추천한다.
- LLM 출력은 검증 후에만 이벤트 시스템에 등록된다.
- LLM이 없어도 시뮬레이션은 작동한다.
- 과거 시점으로 복원할 수 있다.
- 다른 개입을 적용한 대체 역사를 만들 수 있다.
- 두 역사의 차이를 차트와 사건 목록으로 비교할 수 있다.
